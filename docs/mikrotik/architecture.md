# Architecture

`cmd/mikrotik-mcp` loads configuration and the embedded catalog, validates schemas, and starts the selected MCP transport. `internal/mikrotik/config` owns vendor profile settings; `internal/serverconfig` owns common strict TOML loading and listener settings. Profile configuration is immutable after startup; password values are resolved per RouterOS request, and the HTTP MCP token is loaded when its handler starts. Both binaries report version `0.1.0` through `internal/buildinfo`.

`internal/mikrotik/research` and `cmd/mikrotik-cataloggen` are maintenance-only code. The explicit allowlist in `tools/mikrotik/catalog-spec.json` selects operations; manual argument tables provide property metadata. Reviewed overrides supply omitted standard properties and creation constraints. The generated catalog keeps provenance and overrides alongside each operation. This is documentation-based generation, not live command introspection. Source HTML stays under ignored `.cache/mikrotik/manual`; the reviewed specification is versioned, and generated catalog data is embedded from `internal/mikrotik/catalog`.

`internal/mikrotik/catalog` derives MCP input schemas. The shared `internal/mcpschema` package resolves and constructs strict object schemas. Arguments separate `profile`, record `id`, read controls, and RouterOS `parameters`. Properties are exact menu-specific names. Read-only properties are excluded from mutation inputs; the generic RouterOS execution interfaces are never tool arguments. Complex CLI types stay strings because the REST API does not define JSON object encodings for console composites.

`internal/mikrotik/mcpserver` registers operations with the SDK. One engine is shared by stdio and HTTP. Shared `internal/mcphttp` provides stateless Streamable HTTP, bearer authentication, host/origin checks, and response limits. A token grants the same profile access as running the binary locally; there is no per-user authorization. See [common HTTP behavior](../configuration.md#http-transport) for routes, status codes, and limits.

`internal/mikrotik/engine` applies global and profile group restrictions and read-only permissions before obtaining a client. It owns one lazily initialized HTTPS client per profile. Static-only mutations inspect current record status before sending a write. This protects against modifying an already-dynamic entry, but is not an atomic precondition against other administrators. List pagination happens after an entire bounded response is read. Protected profiles additionally require a matching `safe_mode_id` for every mutation, including moves and singleton updates; that MCP control never enters REST parameters.

`internal/mikrotik/safemode` owns a persistent, host-key-verified SSH shell per protected profile, using the profile's password credentials. It acquires RouterOS safe mode without taking over another session, verifies current ownership and history capacity, and serializes writes with confirmation/rollback. Its lifetime belongs to the engine, independently of stdio or individual stateless HTTP requests. Five-second monitoring and checks around every write stop dispatch if protection is lost or floating-undo history reaches 80 actions. A separate confirmation call requires healthy ownership and a fresh REST read. Deadline expiry, explicit rollback, failed writes, and shutdown request rollback; uncertain REST failures retain the guard for a further 65 seconds before deliberate release to cover commands still running on the router. Shutdown waits for that drain before closing clients.

`internal/mikrotik/routeros` constructs HTTPS endpoints from configured hosts, uses Basic authentication, verifies certificates, refuses redirects, and caps decompressed response bodies. The client's ambient proxy support is disabled. Record identifiers are literal RouterOS hexadecimal IDs, with the asterisk left unescaped as required by the REST API. Scalar values are encoded without shell interpretation; singleton updates use POST to `set`, rule movement uses POST to `move` with `.id` and `destination`.

Router response bodies never appear in errors or operational logs. Recognizable secret fields and text assignments are redacted recursively before returning data. Unlabeled secrets in arbitrary text cannot be reliably detected. HTTP request bodies default to 16 MiB (configurable up to 64 MiB); complete HTTP responses are capped at 64 MiB. Router output defaults to 4 MiB per profile. A request/response failure after sending a write can leave its outcome unknown; writes are never automatically retried. Safe-mode state distinguishes active, committed, rollback-requested, and uncertain outcomes. An acknowledged rollback request does not prove restoration. Console exchanges expose only ownership booleans and a history count, never raw undo/redo commands. See [safe-mode behavior and limitations](safe-mode.md).

Offline `--check` validates configuration syntax/defaults and registered tool schemas. It does not load password values, validate CA file contents, authenticate to a router, or prove firmware compatibility. Live discovery reads system resources and packages only, subject to the same `system` group permission as its corresponding tools. Catalog operations use the vendor documentation as their source of support.
